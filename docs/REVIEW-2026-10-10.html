四、缺陷清单（按严重度，含复现方式与修法）

P0同步端点把「后台任务」变成「阻塞请求」——核心链路的体验是假戏

现象：POST /api/chapters/{id}/finish 实测占用 HTTP 请求 13.14 秒（假模型每次 3 秒）；同批的 /summary、/foreshadows/refresh 分别 3.15s / 3.16s。对照组 /generate（async 端点）只用 0.04 秒。

根因：这三个端点在 app/api/chapters.py / books.py 里声明为同步 def，FastAPI 会把它丢进 threadpool 执行；threadpool 线程里没有事件循环，于是 asyncio.create_task() 抛 RuntimeError，被 except RuntimeError 捕获后走了 asyncio.run(...) 兜底——整条链变成在请求线程里同步跑完。stderr 里出现 asyncio.run(_finish_chain(...)) 就是证据。

真实影响：换成你的 DeepSeek Flash 起草一章 2000–3000 字，链上 4 次调用（起草 + 去AI味 + 摘要 + 伏笔）大约 2–6 分钟。这期间：前端 pollTask 要等提交请求返回才会启动，所以"起草 ⏳ → 去AI味 ✓"的逐步进度根本不会出现；用户只能看到一个卡死的界面，任何浏览器/网络中断都会让人以为失败（服务端其实还在跑）。任务最终会跑完、数据不丢，但这一功能的设计意图完全没兑现——而 DESIGN.md 第 109–110 行明确承诺了"逐步状态落库、前端轮询"。

修法（二选一，都只动几行）：

# 方案 A（最小改动）：三个端点改异步，让 create_task 有事件循环可用
-  def finish_chapter(cid: str):
+  async def finish_chapter(cid: str):
      ...   # summary / refresh_foreshadows 同理

# 方案 B（更稳，彻底摆脱"必须在事件循环里"的约束）：
# runner 里用独立线程承载链，同步/异步端点都不会阻塞
-  try: asyncio.create_task(_finish_chain(tid, book_id, chapter_id))
-  except RuntimeError: asyncio.run(_finish_chain(tid, book_id, chapter_id))
+  threading.Thread(target=lambda: asyncio.run(_finish_chain(tid, book_id, chapter_id)),
+                   daemon=True).start()

建议顺带把 except RuntimeError 兜底删掉——它现在扮演的是"静默降级成阻塞"，正是这个 P0 能藏这么久的原因。

P1SQLite 未开 WAL、无写入重试，可能留下永久"正在生成"的僵尸记录

实测：24 线程 × 30 次并发写 → 29/720 次失败（database is locked），耗时 28.84 秒（正常应 <1 秒）。当前 journal_mode=delete、busy_timeout=5000。

为什么现在没炸：日常并发很低（一条链 + 偶尔一次页面操作）。但只要你同时跑两章的「一键写完本章」，或在生成过程中反复编辑章节，写冲突概率就上来了。

放大伤害的一处：runner._run() 结尾的 store.update("gens", ...) 不在 try 里。一旦这里抛错，这条 gen 会永远停在 status='running'——而 chapter_busy() 正是靠 running 判断的，该章会永久锁死，只能重启服务（重启会清理僵尸，算留了后路）。

修法：在 store.conn() 里打开连接时统一执行 PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000; PRAGMA synchronous=NORMAL;， 并把 _run / _llm_once 里所有收尾落库包一层 try/except，失败时至少把状态写成 failed 而不是留 running。

P2网页人工通道可覆盖正在生成的章节

runner.save_web_result() 写完 chapters.content 前不检查 chapter_busy()。若该章正有一条 API 生成在跑，你贴回来的结果会被随后完成的模型输出覆盖（或反之）。同时 save_web_result 也不更新 status/progress，网页通道走完的章节仍停留在"草稿"，与 API 通道行为不一致。

修法：提交前 if chapter_busy(cid): raise HTTPException(409, ...)；并按 step 类型同步 status/progress。

P2前端 6 处弹窗的换行符写错，用户会看到字面 "\n"

实测 static/app.js 里有 10 处 \\n（JS 单引号/模板串里的双反斜杠 = 字面反斜杠+n，不是换行）。受影响：导出目录提示（522 行）、导出结果（526）、模型测试结果（690）、网关模型列表（696–697）、推荐配置结果（709–713）、绑定结果（718–719）。

修法：全局把 \\n 替换为 \n（注意别误伤 D:\\小说导出 这类真正的路径转义——先看一遍上下文再改）。

P2安全面：本地单用户场景下的几处开口

  • 无任何鉴权/CSRF 防护。服务只绑 127.0.0.1（这点做对了），但本机任意进程、或浏览器里被诱导发起的简单请求，都能调用 /api/*（含删除书、读取全部产出）。
  • 导出接口接受任意绝对路径：POST /api/books/{id}/export 的 dir 参数直接 makedirs + 写文件，可写入任意可写目录。建议限定在 data/exports/ 白名单内，或至少校验前缀。
  • 前端 href 未过滤协议：renderWebChannel 直接 href="${esc(r.web_url)}"，若 web_url 填 javascript:... 点一下就会执行。属自伤型风险，加一行协议白名单即可。
  • 密钥明文存 data/app.db：已在 README 与 .gitignore 中说明并做了接口不回显（_mask），可接受，此处只作提示。
