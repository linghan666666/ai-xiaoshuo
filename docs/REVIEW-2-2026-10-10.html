三、这轮改得好的地方

  • spawn() 是正解。不依赖调用方上下文（async 端点挂循环、同步端点起线程），并且把"静默降级兜底"这个祸根直接删掉、还在注释里写明"绝不能再出现"——修根因，不是绕过症状。
  • P1 的修法比我建议的更细致。我原本只说"开 WAL"；实施时发现每连接执行 PRAGMA journal_mode=WAL 反而引入 4/720 的 readonly 错误，于是改成"只在建库时设一次 + 连接级只设 busy_timeout"，并写了注释解释为什么。这是真懂 SQLite 的写法。
  • update_safe() 的动机写得清清楚楚：不是"为了健壮"这种空话，而是"收尾落库一旦抛错，该章会被并发锁永久锁死"——把一个抽象原则落到了具体的故障链上。
  • 把两个已修缺陷做成了常驻回归工具（probe_async.py / probe_db.py），脚本开头写清"为什么存在"且会自己 sys.exit 报错。这正是防止 P0 复发的最好办法。

四、本轮新发现的问题（都是打磨级，但值得修）

P2-a字数保护"管太宽"，而且章节页会说反话

实测（我自己写的探针，慢模型 + 已有 1500 字的章）：

重新起草同一章：旧正文 1500 字，新稿约 300 字
  生成状态 = success（前台会显示成功）
  章节字数：1500 → 1500   （正文未被覆盖）
  记录里的说明：[note] ⚠️ 改写结果字数从 1500 骤降到 300……**未覆盖本章正文**

两个问题：

  • 保护范围越界：守卫写在 _run 的"有 chapter 就检查"分支里，所以对 起草（chapter/draft）步骤也生效。如果你对一章"重新起草"，模型给出一个更短但合法的新稿，会被静默拦下。措辞也文不对题（起草场景却写"改写结果"）。
  • 前端会说反话：app.js 章节页的成功分支硬编码 ✓ 已写入本章（{chars} 字），而"未覆盖正文"的说明存在 g.error 里——成功分支根本不显示它。也就是说：正文没被改，界面却告诉你"已写入本章"。

建议：① 守卫只在改写类步骤（deai/polish/hook/ooc_fix/deai_fix）生效，起草步骤放宽或只告警；② 文案按步骤类型区分（起草=「本次生成字数 X→Y，未覆盖」）；③ 前端成功分支补一句 if (g.error?.startsWith('[note]')) 就把说明显示出来。

P2-b导出白名单与界面提示互相矛盾（而且对你尤其别扭）

实测三种目录：

dir='D:/小说导出'                        → HTTP 400  只允许在「<项目路径>\data」或「C:\Users\<用户名>」之下
dir='<项目路径>/data/exports/自定义'  → HTTP 200  ✅
dir=''（留空）                            → HTTP 200  ✅ 落到 data/exports/<书名>

但前端导出弹窗的提示语仍然写着「可填绝对路径，如 D:\小说导出」——照它填就会 400。而且你的文件习惯本来就在 D:\（项目、台账全在 D 盘），这个白名单等于把你最顺手的落盘位置挡在外面了。

建议：加一个 PLATFORM_EXPORT_DIRS 环境变量放行额外根目录（例如 D:\），并同步改掉那句提示语。

P2-c几处"数字对不上"与注释漂移

  • 冒烟用例数有三个说法：README 第 65 行写"12 组"、第 142 行写"15 组"、FIXES 文件写"17 组"，实际打印 16 个用例段落（编号 1–14，含 9b/9c）。数字不重要，但同一件事三个数是可信度问题。
  • generate 路由的注释已过时：还写着"必须是 async……同步端点跑在 threadpool 里，没有事件循环会直接 500"。现在 spawn() 两种都安全，这句反而会误导下一个读代码的人——正是这类"没说清为什么"的注释让 P0 藏了一整轮。
  • adopt_generation 不查 chapter_busy()：点「采用这条结果」时若该章正有生成在跑，采用结果可能随即被那条生成覆盖。属手动恢复动作，影响小。
  • pyflakes 剩 1 处未用导入（definitions.py 的 typing.List）。
