# 设计说明（DESIGN）

## 一、出发点：为什么"以 skill 为核心"

常见的做法是**先造一台通用节点引擎，再把手册当参考资料挂上去**——
结果是：手册的价值靠"人记得去查"，平台自身的提示词、检查项、流程与手册是两套东西，会各自漂移。

这一版反过来：**手册是引擎，平台是它的执行台**。三条映射：

| skill | 平台 | 实现位置 |
|---|---|---|
| SKILL.md 的工作流 | 流程（步骤清单） | `app/flows/definitions.py` |
| references 的原文指令 | 提示词（不改写） | `app/knowledge/blocks.py` + `flows/runner.py` |
| references 的清单 | 检查项 | `app/knowledge/assets.py` + `checks/checks.py` |

好处很直接：**改手册就能改平台行为** —— 但要看清楚边界（这也是评审指出的问题）：

| 随 skill 自动变 | 不随 skill 变（写死在代码里） |
|---|---|
| 提示词里的指令原文（`blocks.py` 抽取） | **流程的步骤结构**（9 步 / 8 步 / 3 步，在 `definitions.py`） |
| 检查条款（黑名单 / 违禁词 / 自查清单，`assets.py` 解析） | 步骤与模块的关键词映射（同样在 `definitions.py`） |
| 知识库可检索、可阅读的内容 | 检测词表（`checks/vocab.json`，派生物） |

`SKILL.md` 目前只被用来确认"文件在不在"（`library.info()["skill_md"]`）。skill 若新增一个工作流，
需要在 `definitions.py` 里加一段定义才会出现在平台上——这是本版的已知边界，不是"自动同步"。

## 二、知识库层（平台的地基）

skill 的 13 个 md 由原始资料整理而成，结构稳定：每篇原文是一个 `## 📄 原文件名` 节，
平台解析成「模块 → 节」两级索引（当前 13 模块 / 128 节 / 35.2 万字，按 mtime 缓存）。

- `library.py`：索引、全文读取、关键词检索（AND 语义，界面用）。
- `blocks.py`（核心）：**指令块抽取**。步骤只声明"去哪些模块、用哪些关键词"，
  抽取器按「标题命中×3 + 正文命中 + 指令特征词 + 节长度」打分挑出最相关的原文节，
  并额外给出 `directive` —— 从节正文里的「指令：」「【指令X：」处切出的**可执行段落**。
  这就是为什么平台不需要自己编提示词：手册里的措辞是反复调过的，原样用最好。
- `assets.py`：把清单类内容解析成结构化项 —— 黑名单（8 组）、违禁词清单（一级/二级/三级 + 子类）、
  违规情节自查表、投稿自查核对清单（`□` 11 项）。解析规则写在函数注释里（含判据来源）。

## 三、流程层（skill 的工作流）

`definitions.py` 里三个流程：

- **long_novel 长篇开新书（9 步）**：选题定方向 → 合规预检 → 书名与简介 → 人设档案（先锁人设）→
  大纲与长线 → 黄金三章 → 章节续写 → 去 AI 味 → 投稿前自查。对应 SKILL.md 工作流 A。
- **short_story 短篇工业化（8 步）**：三份基础设定表 → 五章分章大纲（指令1）→ 大纲三项核查 →
  单章正文（指令2）→ 三层加工 → 章尾钩子（指令5）→ 全文漏洞扫描（指令6）→ 投稿终稿核验。对应工作流 B（严格照 06 模块）。
- **stuck 卡文/人设崩坏急救**：卡文自检定位 → OOC 即时纠错 → 去 AI 化补强。对应工作流 C。

每步的 `modules / keywords / inputs / check` 四要素决定它的行为；`stage` 区分全书级（做一次）
与章节级（对某一章反复做）。**要加一步、改一步，只改这个文件。**

## 四、提示词组装（runner.build_prompt）

```
# 任务：{步骤号}. {步骤名}          ← 目标
## 本书资料                        ← 书名/题材/受众/一句话设定
## 已确定的设定与前序产出            ← inputs 指定的前序步骤产出（人设档案、大纲…）
## 番茄写作手册 · 本步依据           ← 抽取到的 skill 原文节（带出处）+ 章节级步骤自动追加赛道模块
## 本次要写的内容                   ← 章节级：本章要点 + 上一章结尾节选 + （改写时）本章现有正文
## 补充要求                        ← 用户本次额外指令
## 输出要求                        ← 章节=只出正文（不写标题行）；其他=只出成品
```

原文指令放在"依据"位置而非系统提示，是为了可核对、可复制、可追溯：
运行详情里能回看这次用了哪几块原文、完整提示词是什么、哪个模型出的。

## 五、数据模型（store.py）

| 表 | 作用 |
|---|---|
| `books` | 书：题材/受众/一句话设定 + 走哪条流程 + 当前步骤 |
| `artifacts` | 每一步的产出（键=步骤 id），可锁定（锁定后生成不覆盖） |
| `chapters` | 章节正文（不存标题行，标题单独存；导出时拼「第N章《标题》」） |
| `gens` | 所有模型调用留痕：提示词、输出、模型、耗时、错误、备注 |
| `checks` | 三条检查的历史结果 |
| `models` | 模型/通道配置（含网页版人工通道） |

## 六、检查层

- **黑名单预检**：命中检测（用 `vocab.json` 的检测词表）+ 逐条列出手册红线条款供人工确认。
  预检不替用户下"能写/不能写"的结论，只把命中与原文摆出来。
- **违禁词与 AI 痕迹**：一级命中即判不通过；二三级只提示并给替换建议；另附字数/段落/对白占比/章尾钩子检查。
- **投稿前自查**：清单纯解析自 01 模块（11 项）；其中"字数核对 / AI 痕迹 / 开篇核对 / 章节钩子"
  四项会给出自动证据，其余靠人工勾选。全部勾选才判通过。

检测词表（`app/checks/vocab.json`）是**派生物**：原始条款里的词是打码写法（GJ / Z治 / ZZ），
无法直接扫描，故做了人工整理版并在文件头注明来源与"以原文为准"的原则。

## 七、模型接入与分工

- OpenAI 兼容（DeepSeek / 智谱 / Kimi / 火山方舟 / 各家网关均可）：流式（防长文超时）、
  可关思考（推理型模型必开）、思考通道正文抢救、跳过系统代理。
- **网页版人工通道**：不调用、不代点网页，只把提示词交给你，你执行后把结果贴回来（合规且稳定）。
- 生成走后台任务（gen_id + 轮询），长文不会卡住 HTTP，也避免超时丢结果。
- **改写保护**（实测教训）：改写类步骤的输出要求显式禁止压缩篇幅；落地时若**字数骤降 <60% 或暴涨 >3 倍**，
  不覆盖正文、把结果留在生成记录并写明原因（`_run` 里 `shrink / blowup` 判据）。
  实测：修前 GLM 把 3178 字压到 883 字（-72%），修后 3521 → 3236 字（-8%）。
- **采用/回滚**：`POST /api/gens/{gid}/adopt` 把任一条历史生成结果写回目标（正文/产出/摘要/伏笔台账）——
  既服务"被保护拦下后手动采用"，也让"回滚到上一版"成为可能（生成记录即版本历史）。
- **模型分工（依据 02a《AI 模型适配使用建议》）**：两个档位 ——
  ⚡省钱档（起草 DeepSeek Flash，一章约 ¥0.03）/ ⚡质量档（起草豆包 Seed 2.1 Pro，一章约 ¥0.1–0.15），
  改写固定 GLM-5.3 Flash、大纲 DeepSeek V4 Pro、扫描 Kimi K2.6。
  `POST /api/models/presets`（body.tier=value|quality）—— 拉取网关真实模型列表 → 按角色关键词匹配 →
  建好 4 条并设好参数与开关（GLM 不勾关思考）。**不猜模型名**，id 全部来自网关返回。
- **步骤级默认模型**：`books.step_models`（JSON：`{"chapter":"mdl_x"}`）；解析顺序
  **本次指定 → 本书该步骤绑定 → 全局默认**（`runner.resolve_model_for_step`）。
  `POST /api/books/{pid}/step-models/apply-presets` 可按角色把这套分工绑到本书对应步骤
  （角色→步骤映射见 `api/books.py` 的 `ROLE_STEPS`）。

## 八、跨章连贯与任务链（本轮补齐）

**为什么重要**：长篇最大的风险是"写着写着人设漂了、伏笔埋了忘收、跨章剧透"。逐章把前文全文喂给模型
既贵又稀释注意力，所以用**摘要通道 + 伏笔台账**两样轻量结构替代：

- `chapters.summary`：每章生成后由模型产出结构化摘要（关键情节/出场人物/**人物状态变化**/遗留悬念/衔接提示），
  结构的选择是为了让下一章能读到"人变成什么样了"——这正是人设漂移最容易发生的地方。
- `books.foreshadows`：伏笔台账，每章由模型**整段重写**（新埋的追加、已回收的删除，拿不准就保留）。
  起草时注入，要求"有合适时机就推进/回收，回收了要写清怎么落实"。
- 注入位置：仅对**写新正文**的步骤（`chapter` / `draft`）注入，改写类步骤不注入（省 token）。
  前情摘要默认最近 6 章（`CONTEXT_SUMMARY_CHAPTERS`），更早的只报数量。
- ⚠️ 改了正文之后要重算摘要（章节页有「重算摘要」按钮），否则下一章读到的还是旧摘要。

**任务链**（`tasks` 表 + `runner._finish_chain`）：「一键写完本章」= 起草 → 去 AI 味 → 摘要 → 伏笔 → 违禁词扫描，
逐步状态落库、前端轮询。链式执行里**只有一处模型调用点**（`_run`），避免重复计费。

**可靠性补齐**：同章节并发锁（`chapter_busy`）、`retry_generation`（原提示词重试）、
`clear_stale_running`（重启清理僵尸 running）、启动自动备份（`store.backup`，保留 10 份）。

## 九、已验证

- `python tools/dev/smoke_test.py --inproc`（进程内，不占端口）：**14 组全绿** —— 知识库（13 模块 / 128 节 /
  检索 / 指令块 / 黑名单 / 自查清单 / 本机对比）→ 模型配置与连通测试 → 建书与流程 → 步骤面板（含工具箱借流程）→
  生成并自动落库 → 黑名单预检 → **一键写完本章 5 步链** → **跨章摘要与伏笔注入** → 生成记录重试 →
  三检查 + 全书批量扫描 → 步骤级默认模型 + 一键推荐配置 + 绑定总览 → 导出（标题规范）→ 清理。
- `pyflakes app/ tools/`：未定义名称 0；前端 `app.js` 语法校验通过、DOM id 引用核对无缺。
- ⚠️ 尚未用**真实网关**跑过（需要你自己的 API Key）：模型连通性请先用「模型」页的「测试」按钮确认。

## 十、边界与后续可做

- 检索是**关键词匹配**，不是语义检索：题材用词与手册不一致时可能抽不到块（此时提示词里就只有本书资料）。
  改进方向：给步骤的 keywords 增加同义词，或未来接向量检索。
- 章节连贯已落地（见第八节）：前情摘要（最近 6 章可调）+ 伏笔台账 + 上一章结尾节选；更早章节只报数量不逐章注入，若写到 100+ 章仍觉不够，可再加"卷级摘要"压缩层。
- 手册 04 模块（签约/首秀/稿费）与 07（同人）已内置可查，但还没有对应流程；
  若要做"签约后阶段"的流程，按 `definitions.py` 加一个 flow 即可。
- 伏笔台账已落地（`books.foreshadows`，每章由模型整段重写，起草时注入）；
  **单元结构表 / 逐章细纲、结构化人物卡**（按出场章节裁剪防剧透）仍未做——长篇连载到几十章后建议补上。
